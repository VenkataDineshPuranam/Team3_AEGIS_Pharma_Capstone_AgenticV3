Security posture — controls held, deployment surface shifted

Not one governance-critical control differs between the snapshots. Every V3 security-relevant change is in the supply chain and the deployment path — which is also where two of them cost something the documentation hasn't caught up with.

Held

ADR-004's three defence layers, the retrieval-boundary evidence gate, fail-closed policy load, the ten hook bindings, the prompt guard's pattern set, and the AI-SBOM verifier are byte-identical.

The four security-relevant deltas

IMPROVES

Inference moves inside the Azure boundary. V2's runtime calls api.anthropic.com directly. V3's default routes through Azure AI Foundry, which is precisely the billing/networking/governance containment ADR-009 chose Route A for.

Cost: the inference secret count goes 1 → 3. All three are ACA secrets referenced by secretref:, so none is visible in az containerapp show.

IMPROVES

Failures stop being invisible. evidence_retrieve now logs the real exception before graph.py converts it into a bare dependency_unavailable abstention. The caller still sees nothing — BC-2 is intact.

Mild tension: the log line carries raw driver exception text, and Stage 17's redaction ruleset governs trace writes, not application logs. Low risk in batch_review (no PHI); revisit when PV Intake carries case narratives.

COSTS

Build provenance became best-effort. Both attest-build-provenance steps now carry continue-on-error: true, because GitHub refuses attestation on user-owned private repos. The workflow comment is candid that this is "a real gap worth knowing about."

That gap is not reflected in residual_risk_register.md §3 (T-10, supply chain), which is identical in both snapshots. The AI-SBOM's prompt hashes are only as strong as the link between repo and running image — which is the link that just became optional.

COSTS

A static registry credential entered the deploy path. CD now calls az containerapp registry set with ACR_USERNAME / ACR_PASSWORD so Container Apps can pull the image with its own identity. Necessary — the runner's docker login does not transfer — but it is a long-lived shared secret alongside the existing OIDC AZURE_CREDENTIALS, and a managed identity with AcrPull would achieve the same without one.

Both new secrets are also missing from the required-secrets list documented at the top of cd.yml and are not checked by the preflight job — so a missing value fails later, inside an az command, which is the exact failure mode preflight exists to prevent.

AI bill of materials

ai_sbom.json is the only substantive non-code file that differs between the snapshots — and the difference is the interesting kind. The AI-BOM exists to catch a governance artifact drifting from its recorded hash. Between V2 and V3, it caught one.

At V2's HEAD the AI-BOM records a hash for tool_manifest.json that does not match the file's own content. V3's regenerated BOM matches. Verified by recomputing every hash in both trees.

The drift, and how it was separated from a false alarm

Run verify_ai_sbom.py on a Windows checkout and both snapshots report three mismatches — which is a line-ending artifact, not a finding. The generator hashes raw file bytes, and git checks these files out with CRLF on Windows while the hashes were computed on LF. Normalizing to the LF form that git stores and that CI's Ubuntu runner sees separates the artifact from the real result:

Hashed artifactV2 recordedV3 recordedActual content (LF)Verdict
policy_contract.v1.json c37c1e44891b…c37c1e44891b…c37c1e44891b… Matches in both
tool_manifest.json 1581026e90ca…47cb0fdb44e5…47cb0fdb44e5… V2 drifted · V3 correct
sbom.json db91beb7683b…db91beb7683b…db91beb7683b… Matches in both

The manifest file itself is byte-identical across the two snapshots. So this is not a change V3 made to the manifest — it is V2's BOM having been stale at its own HEAD, and V3's regeneration commit closing it. On CI's Ubuntu runner, V2's governance job fails the AI-BOM check; V3's passes.

This is the control working as designed. The tool manifest is the artifact that enumerates what tools exist and what they may do — precisely the kind of file whose silent change should be loud. tests/security/test_ai_sbom_verification.py proves the mechanism by actually making a weakening edit to a system prompt and asserting the build goes red. Here it caught a real drift with no test needed.

What the AI-BOM refuses to claim

HONEST LIMIT

A matching model id proves nothing about the weights serving the request. Both model components are marked identifier_is_mutable_alias: "true", and verification reports an id change as a finding, not a failure — because pretending an alias is a pin would invite the reader to stop asking the question that matters.

ADR-009's revisit trigger (re-run Stage 14 baselines if the served model changes) applies here and this file explicitly cannot detect it.

V3 GAP

The new provider is not in the BOM. V3 added AzureFoundryLLM and made it the default, but the AI-BOM still lists exactly two models — claude-sonnet-4-5 and llama-3.1-8b-instant — with no component for the Foundry deployment that now serves production traffic.

Defensible in that the underlying model is unchanged and the deployment name lives in a secret. But the BOM's own purpose is recording what determines behaviour, and "which endpoint answers" is now a different answer than it records.

BOTH

Stale identity. The BOM's bom-ref is aegis-pharma-v3 in both snapshots, while the repo's renumbering pass now calls this system V2. Cosmetic, but it is the identifier a customer's security tooling would key on.

Both verifiers run in CI's governance job and again at API container startup, so a drifted BOM fails the build and refuses the boot — not merely a report someone has to read.

EU AI Act — the classification, and what it deliberately does not claim

The classification is explicitly labelled reasoned, not a legal determination, and is recorded as open gap G-1 rather than quietly treated as settled. That framing is identical in both snapshots and is the most defensible thing in the pack.

The two clauses V3 actually moved

CLOSES

Logging / record-keeping — the audit write could not survive a real deployment. graph.py opens one SQLite connection per request and closes over it from every node from intake to finalize; LangGraph's runner dispatches those nodes onto different worker threads. In V2 that trips Python's same-thread guard and raises.

This matters more here than an ordinary bug would. The audit write is not best-effort logging — it is the clause. finalize's own rule is that a response reaching the caller with no audit record is not a valid terminal state, and the compliance evidence index rests its strongest claim (99+ AgentRun rows, zero silent completions) on that path working. V2's evidence was collected on a single-threaded local run; V3 is the first snapshot where the same guarantee survives a multi-threaded container.

WIDENS

Third-party / supplier relationships — already Gap G-2, now with less provenance. Both attest-build-provenance steps became continue-on-error: true, so a deployed image may now carry no signed link back to the source that built it. A static ACR username/password also entered the deploy path alongside the existing federated credential.

Neither is reflected in gap_assessment.md G-2, which is identical in both snapshots. The AI-SBOM's per-prompt SHA-256 hashes are only meaningful if the running image provably came from the hashed repo — which is precisely the link that became optional.

SHIFTS

Data governance — the model provider moved inside the tenancy boundary. V2's runtime calls Anthropic directly; V3 defaults to a model deployed behind Azure AI Foundry. That is the containment ADR-009 chose Route A to get, and it changes where prompt content travels.

Whether that also improves data residency depends on the Foundry deployment's region, which lives in a secret and cannot be verified from either repository. Worth confirming before citing it as a compliance improvement.

The Lean critique of V3, in its own vocabulary. The DMAIC plan's governing rule is that instrumentation and evidence acquisition outrank feature scale-out, because "nothing has been measured from a running system." V3 did the work that makes measurement possible — a deployable image, a one-command local stack, a working CD path — and then took no measurement. That is not waste in the register's sense; it is the correct prerequisite. But it means the single Unknown that RR-1 says could reopen ADR-008 is exactly as Unknown as it was eleven commits ago, and V3 is the first snapshot where measuring it would have been cheap.
What the discipline got right. Every one of the four root causes is traced to the register rows it explains, every accepted residual risk carries a named re-decision trigger, and the plan states plainly that topology was locked before the cost number existed rather than presenting the sequencing as clean. A register that records its own violated precondition is doing the job.

Design positions carried into both snapshots unchanged

Unchanged
No planner agent
A deterministic router plans. The sequence is a constant; a planner would be an LLM re-deriving something already written down — and a new authority surface that could skip a gate.
Unchanged
Guard runs twice
Before and after the Critic, because the Critic is itself an LLM node and its approve verdict is the transition that reaches a human.
Unchanged
Critic never duplicates a gate
If a check is a lookup, a type, or a pattern match, the Critic doesn't do it. It exists only for checks that require reading the argument.
Unchanged
No cross-run memory
Deliberate. It is why T-07 (context poisoning across runs) is marked not-applicable rather than mitigated.
What the identity of these files proves. A design whose agent topology has to move when the model host moves was coupling orchestration to inference. This one didn't move — the graph, the authority limits, the loop guards and the stop conditions are the same bytes on both sides of a provider change and a platform change.
